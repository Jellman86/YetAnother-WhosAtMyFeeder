This release is about notifications that take you straight to the bird, and a feeder that keeps
classifying when a model is slow to start. If your Home Assistant sidebar has ever stopped answering
after a settings change, this is the update for you.

## What's new

- **Notifications open the detection.** Set **Instance address** under Settings → Notifications to
  the address you use to open YA-WAMF, and every notification links to the visit it announces: the
  Discord title, a **View detection** button in Pushover and Telegram, and the email button. Choose
  **Frigate** under **Notification link opens** to land on the same tracked object in Frigate's
  Explore page instead (Frigate 0.15 or newer, using the Frigate public URL from Integrations).
  Leave the address blank and notifications look exactly as before.
- **A model that is slow to load no longer stops classification.** A worker that took more than
  twenty seconds to compile its model for the NPU was killed and restarted until none was left, and
  detections were dropped as "worker unavailable". The first load now gets the same three-minute
  window as the rest of startup. If the workers cannot start at all, detections are classified
  in-process instead of dropped, and the Detection tab says why.
- **The Detection tab names the runtime that is actually classifying.** Before the first bird of the
  day it says which runtime will load and that it loads on first detection. Once a worker has
  loaded, the tab and inference health report what that worker runs, not the idle default of the
  process that serves the pages.

## Smoother everyday use

- **Your session token stays out of URLs and proxy logs.** Snapshots, thumbnails, clips and the live
  stream used to carry your week-long session token in their address, so any proxy in front of
  YA-WAMF that logs requests kept copies. Media now uses a browser cookie that only read-only media
  routes accept, and the live stream opens with a single-use ticket that expires after sixty
  seconds. A signed-in browser switches over on its next page load; nothing to do.
- **Counting the media cache no longer freezes the interface.** On slow or network-backed storage,
  the once-a-minute cache count behind Settings could stall every request for seconds, which is why
  clearing the cache made things fast again for a while. The count now runs off the request thread,
  requests that arrive during a count share it, and a slow count is logged with its duration and
  file count for the next diagnostics bundle. The startup identity pass also gives its database
  connection back while it resolves names, so the dashboard's first load after a restart no longer
  waits behind it.
- **The Home Assistant sidebar survives a settings change.** Changing the integration's options used
  to leave the sidebar pointing at the old address with a login nothing refreshed, until Home
  Assistant was restarted. The integration is now 1.1.0: the panel is replaced cleanly, the proxy
  refreshes its login, a rejected credential opens Home Assistant's reconfigure prompt, and the Last
  Bird sensor goes unavailable when YA-WAMF cannot be reached instead of holding a stale value.

## Before you update

- **No special steps.** No schema changes and no settings to revisit. If you use the Home Assistant
  integration, copy the `custom_components/yawamf` folder from this release over the one in your
  Home Assistant `config/custom_components/` and restart Home Assistant to get the 1.1.0 sidebar
  fix; the feeder itself works with either version. Unsuffixed image tags remain the full
  compatibility image; see [hardware acceleration](../setup/hardware-acceleration.md) if you use a
  provider-specific flavour.

## Good to know

- **The retention card says what cleanup does.** Settings → Data promised a 3 AM cleanup. Cleanup
  runs once when the container starts and then every 24 hours from that moment; the card now says
  so in every language the app ships.
- **Every image names its commit.** `docker inspect` shows `org.opencontainers.image.revision`,
  `version` and `source` labels, so a running container can be tied to its exact build. The update
  prompt is unchanged.
- **The CUDA images stay on ONNX Runtime 1.26 on purpose.** Newer releases ship CUDA 13 userspace,
  which needs the NVIDIA 580 driver series on the host; that move is planned for 3.0 and announced
  as such. The CPU and Intel images run ONNX Runtime 1.29.
